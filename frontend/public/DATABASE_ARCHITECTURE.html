💳 2. Chapa Payment Lifecycle Sequence
sequenceDiagram
    autonumber
    actor Guest as 🌟 Guest
    participant UI as React UI
    participant API as Express API
    participant DB as PostgreSQL (16)
    participant Chapa as Chapa Gateway

    Guest->>UI: Selects Pay & confirms booking amount (ETB)
    UI->>API: POST /api/payments/initialize (Rate Limited)
    API->>DB: INSERT INTO payments (status='PENDING', tx_ref, idempotency_key)
    API->>Chapa: POST /transaction/initialize (Server-Side Secret Key)
    Chapa-->>API: Returns checkout_url
    API->>DB: UPDATE payments SET checkout_url
    API-->>UI: Return checkout_url
    UI->>Guest: Redirect to Chapa hosted payment page
    Guest->>Chapa: Enters payment details & confirms
    Chapa-->>API: POST /api/payments/chapa/webhook (or user return)
    API->>API: Validate HMAC signature (x-chapa-signature)
    API->>Chapa: GET /transaction/verify/:txRef (Server-to-Server Verification)
    Chapa-->>API: Returns verified status, amount & currency
    API->>API: Check amount & currency match local record
    Note over API,DB: Atomic PostgreSQL Transaction
    API->>DB: UPDATE payments SET status='SUCCESSFUL', paid_at=NOW()
    API->>DB: INSERT INTO folio_transactions (type='PAYMENT', amount)
    API->>DB: UPDATE folios SET balance = balance - amount
    API->>DB: UPDATE bookings SET paid=TRUE, status='CONFIRMED'
    API-->>UI: Realtime push: Payment confirmed!
🛡️ 3. Security and Payment Safety Checklist (Implemented & Verified)

All 14 security, data integrity, and compliance requirements have been implemented and verified via automated test suites.

✓
Chapa Secret Key Backend Only: Loaded securely into chapaService.js from process.env; never exposed to React browser code.
✓
.env Git Exclusion: .env is excluded in .gitignore and clean .env.example template is committed.
✓
HTTPS in Production: Helmet CSP, HSTS headers, and proxy trust enabled in Express.
✓
Direct Server-Side Verification: Every successful payment is verified via GET /transaction/verify/:txRef before posting.
✓
Amount & Currency Matching: Backend rigorously validates that verified amount and ETB currency match local pending records.
✓
Strict Idempotency: Duplicate webhook/callback triggers are detected; cannot duplicate folio entries or payments.
✓
Webhook Signature Validation: HMAC SHA256 timing-safe validation on x-chapa-signature.
✓
Protected Payment Actions: Reconcile and refund endpoints require JWT authentication and Role-Based Access Control.
✓
Guest Scope Isolation: Authenticated guests can only inspect their own payments and bookings.
✓
Admin Audit Logging: Refunds and ledger adjustments are logged as immutable entries in activity_logs.
✓
Zero Card Data Retention: No credit card numbers, CVVs, or bank secrets are ever stored in PMS tables or logs.
✓
Active Rate Limiting: Enforced on /api/auth/login, /api/bookings, and /api/payments/initialize.
✓
SQL Parameterization: Parameterized queries ($1, $2, ...) eliminate SQL injection vulnerabilities.
✓
Sensitive Field Access Control: Passwords, ID scans, and personal secrets are excluded from standard audit logs.
